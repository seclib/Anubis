# ANUBIS Cleanup Plan

Source basis: audit results only.

Date: 2026-06-05

## Objectives

- Remove dead code and generated artifacts.
- Remove obsolete service facades and alias modules.
- Merge duplicated functionality without losing tested behavior.
- Simplify architecture around one canonical runtime.
- Preserve CLI, Docker, graph runtime, living-loop tests, security guarantees, memory/retrieval behavior, plugin behavior, and research swarm behavior during migration.

## Non-Goals

- No feature additions.
- No dependency expansion.
- No runtime behavior changes without tests.
- No production deployment changes.
- No removal of tested behavior until a replacement path is verified.

## Architectural Decision

Adopt `core.graph` plus `core.bootstrap` as the canonical active runtime because the audits identify it as the active CLI/Docker path:

```text
bootstrap.py
  -> core.bootstrap.main
  -> core.graph.GraphOrchestrator
```

Treat `src/anubis` as a secondary living-loop and compatibility layer until its unique capabilities are either merged into canonical contracts or formally deprecated.

## Cleanup Phases

Rollback strategy:

### Phase 3: Merge Agent Contracts

Goal: reduce duplicated agent descriptors, registries, and executor concepts.

- `core/agents/*`
- `src/anubis/agents.py`
- `src/anubis/agents_life/*`

Steps:

1. Define a canonical `AgentDescriptor` shape.
2. Define one canonical agent result envelope.
3. Build adapters:
   - sync stateless agent adapter for `core/agents`
   - async task-handler adapter for living agents
   - research-agent adapter for `agents/*`
4. Rename or document top-level `agents/` as research-hive agents.
5. Move shared selection logic into one registry contract.

Rollback strategy:

- Keep old registries behind adapters until all tests pass.
- If an adapter breaks behavior, switch callers back to previous registry implementation.

## Rollback Model

Use phase-level rollback:

- Each phase should be one or more small commits grouped by category.
- Do not combine generated-artifact cleanup with runtime refactors.
- Do not combine contract merges with deletion commits.
- Maintain compatibility adapters until replacement behavior is verified.
- For high-risk phases, keep old implementation behind a temporary adapter for one release cycle.

Rollback decision criteria:

- Any security test failure: revert current phase.
- Any bootstrap graph path failure: revert current phase.
- Any memory/retrieval behavior regression: revert current phase unless adapter fix is obvious.
- Any plugin sandbox bypass/regression: revert current phase.
- Any Docker hardening regression: revert current phase.

## Preservation Checklist

Before removing any code, verify:

- The active CLI entrypoint still uses `core.bootstrap`.
- The graph node order remains stable unless explicitly changed.
- Sandbox validation remains mandatory before graph task success.
- Runtime dependencies remain empty.
- Docker default network remains disabled.
- Auto-refactor remains proposal-only.
- Research swarm tests still pass if `agents/*` is renamed or adapted.
- Living-loop tests still pass until the living runtime is formally retired.

## Final Recommendation

Start with repository hygiene and deprecation boundaries, not large refactors. The biggest simplification will come from merging contracts, but deleting implementation code before the contracts are unified would risk losing tested behavior. The safest cleanup strategy is:

```text
clarify -> deprecate -> adapt -> merge -> verify -> remove
```
